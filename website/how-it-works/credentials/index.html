Where credentials live

Credentials are kept in an encrypted store on the host, protected by a local key or a passphrase, or as references to 1Password items that the host resolves after authorisation. Agents never read the store.

How an agent uses one

Services are defined in YAML with named capabilities, such as Slack's reader. You authorise one agent for one capability with one credential. The agent fetches its own scoped sgw_ token from the Agent API and sends it in the service's usual header. The checkpoint checks the request against the capability, then replaces the token with the real credential on the way out. By default it injects credentials only over HTTPS.

Another agent, another destination, or a method or path outside the capability cannot use that token. The upstream service still applies its own permissions.

Secrets the agent brings

The credential guard scans selected request headers for credentials. With the default controls, an unknown bearer token needs approval; effective policy controls header selection, exclusions and the decision. The guard also checks the JSON refresh credential at the supported Codex token endpoint. Other bodies, query parameters and URL paths are outside credential scanning; you can separately enable secret-pattern scanning of bodies and URLs.

Routine credential events contain keyed fingerprints rather than detected raw values. Optional stored flows can retain ordinary headers and payloads, including raw credentials; the gateway-injected credential header is redacted. See the credential-detection and retention limits.

Coding-client logins too

Claude Code and Codex subscription logins can stay in the host vault: the client in the guest sends a scoped token, and the host renews the real login.

What this gives you

  • Gateway access while the real service credential stays on the host
  • Access scoped to one agent, one capability and one credential
  • Credential checks in inspected locations under effective policy

What it does not do

  • Override the upstream service's own permissions
  • Protect logins that a host script copies into the guest, which is a separate, weaker option
