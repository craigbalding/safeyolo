Jobs run on the host

A job is disposable, host-only execution from a trusted job definition, with its output captured as evidence. Jobs run in gVisor, a VZ microVM, or Hyperlight, with core Rust guests or Unikraft Python. A job definition never carries a host mount path.

A binding turns a job into a gate

Running a job does not create a gate. You adopt a binding in policy, and the checkpoint enforces it whatever the agents' prompts say:

BoundaryWhen it runsIf it fails
admit_issueBefore work is created, claimed or continuedThe work is held
verify_outputAgainst the exact bytes an agent publishesAcceptance is held
after_completeAfter completion, as a follow-up actionReported; completion stands, and the action is not retried blindly

Evidence the agents cannot fake

A gate job has no network of its own. When it needs a service, the host makes a mediated call with a scoped token the job never receives, and keeps the exact response bytes and digests. A manual preview, a caller-supplied result or a guest-supplied timestamp cannot satisfy a gate.

What this gives you

  • Checks that hold at every handoff, not just when someone remembers
  • Results tied to the exact output reviewed
  • A gate that applies however the work was created

What it does not do

  • Create a gate just because a job exists
  • Undo a completion when a follow-up action fails
