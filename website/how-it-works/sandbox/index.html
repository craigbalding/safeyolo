Two platforms, one boundary

On Apple Silicon macOS, each agent runs in a hardware-backed microVM built on Apple's Virtualization.framework. On Linux, it runs in rootless gVisor inside an unprivileged user namespace, so launching agents needs no host sudo. Both use the same Debian guest image.

The Linux runtime is bundled with SafeYOLO: gVisor built from a pinned upstream release with three small patches. One limits host Unix sockets to the agent's own proxy socket. One makes directory opens that must not follow symlinks behave as they do on Linux. One keeps a forwarded connection's reply after the sender finishes. The patches and their reasons are in the repository.

No network interface

The sandbox has no external network interface. On macOS there is no virtual network card at all, only virtual sockets. On Linux, the sandbox's network namespace has only loopback, and the one host socket SafeYOLO mounts into it is the agent's own. Requests go from a forwarder inside the guest, through that agent's socket, to the checkpoint. Removing proxy settings inside the guest does not create another route.

Root inside, not on your host

Agents start as an ordinary user and can use sudo to install packages and administer their guest. Guest root is not host root: on Linux it maps to an unprivileged subordinate user on the host.

What persists

LocationBehaviour
/home/agent and /workspacePersist across ordinary stop and run cycles, including tools installed with mise
OS packagesKept by microVMs in their per-agent overlay; discarded on stop under Linux gVisor, with package downloads cached for quick reinstalls
/tmpTemporary, and may be held in memory

What this gives you

  • A separate machine per agent, with its own identity
  • No direct route from the agent to the Internet
  • Only the host folders you explicitly mount

What it does not do

  • Protect data in a writable mount from the agent working in it
  • Make a destructive change harmless because it happened in a sandbox
