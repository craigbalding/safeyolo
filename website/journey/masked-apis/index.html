The problem with handing over tokens

An agent with a token in its environment can send that token anywhere, use it for anything the token allows, and leak it in a log. Scoping the token at the vendor helps, but the secret is still in the sandbox.

What you do

Use the host account owning a running instance with Alice's trusted listener already configured. This example selects the default installation and instance at $HOME/.safeyolo; for another instance, change both paths. Obtain a Slack token for the account you intend Alice to use. The credential guide covers listener setup, storage and verification.

These commands store the token and activate Slack's read-only reader capability for Alice. --allow-host-network also permits host-wide network access to slack.com; the service authorization remains scoped to Alice. credentials add prompts without echo and replaces any existing slack-account credential. On the first write, choose encrypted local storage or passphrase protection; enter q to cancel before creation.

"$HOME/.safeyolo/bin/safeyolo" --instance-dir "$HOME/.safeyolo" credentials add slack-account
"$HOME/.safeyolo/bin/safeyolo" --instance-dir "$HOME/.safeyolo" services authorize alice slack --capability reader --credential slack-account --account operator --allow-host-network
"$HOME/.safeyolo/bin/safeyolo" --instance-dir "$HOME/.safeyolo" services authorized alice

The last command shows Alice's current service token, credential reference, account, capability and routes. An upstream request still needs sufficient Slack permissions.

What the agent does

  1. It fetches its own scoped sgw_ token from the Agent API, using the identity of its socket.
  2. It sends that token in the service's usual header, like any API client.
  3. The checkpoint checks the method and path against the capability, then replaces the token with your real credential on the way out.

Another agent, another destination, or a method or path outside the capability cannot use Alice's token. The service still applies its own permissions.

When it needs more

The agent needsWhat happens
A capability it does not haveIt requests that capability with a reason. Approval authorizes the newly selected access for the named agent, account and credential.
One route the capability does not coverAn eligible missing-route challenge can be escalated for temporary access. Approval adds the recorded method and literal path with the existing credential, for the reported run and lifetime.
A risky route already admitted by the capabilityAuthored risk policy may allow, deny or require approval. A risk grant can last once, for the session, or remembered; it stays within the admitted capability.

A temporary route grant leaves query and body values unrestricted unless an enforced contract bounds them. It does not imply access limited to a sample repository or payload. Other network, credential, contract and risk controls still apply. Approval does not replay the blocked request; the agent must retry explicitly.

The same pattern, many services

  • GitHub over HTTPS, including Git pushes governed by authored risk policy
  • Docker and Compose, with each management request checked against the gateway capability
  • Coding-client subscriptions: Claude Code and Codex logins stay in the host vault and are renewed on the host
  • Services hosted by other agents, shared through the same gateway
  • Your own APIs, described in YAML, with optional effect models that assess what a permission could do

What the gateway gives you

  • The configured service credential stays on the host
  • A token works only for its agent, capability and destination
  • Unknown credentials in selected request headers require approval under the default controls

What it does not do

  • Scan general bodies, query parameters or URL paths for secrets; the supported Codex refresh endpoint has a specific body check
  • Remove ordinary raw credentials from optional stored flows; the injected credential header is redacted
  • Override the service's permissions or make command-execution authority harmless
  • Protect logins a host script copies into a guest, which is a separate, weaker option
