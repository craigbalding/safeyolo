The problem with handing over tokens

An agent with a token in its environment can send that token anywhere, use it for anything the token allows, and leak it in a log. Scoping the token at the vendor helps, but the secret is still in the sandbox.

What you do

On the host, store the credential and authorise one agent for one named capability. For Slack's read-only reader capability:

safeyolo credentials add slack-account
safeyolo services authorize alice slack --capability reader --credential slack-account --account operator --allow-host-network

credentials add prompts without echo, so the secret never appears in your shell history. The store is encrypted on the host, or points at 1Password.

What the agent does

  1. It fetches its own scoped sgw_ token from the Agent API, using the identity of its socket.
  2. It sends that token in the service's usual header, like any API client.
  3. The checkpoint checks the method and path against the capability, then replaces the token with your real credential on the way out.

Another agent, another destination, or a method or path outside the capability cannot use Alice's token. The service still applies its own permissions.

When it needs more

The agent needsWhat happens
A capability it does not haveIt requests that capability with a reason; you approve or decline it
One route the capability does not coverIt gets a route challenge with the exact recorded scope, and can ask for temporary access to that one route
A risky route, such as a Git pushYou see a specific request, for example alice wants to push to craigbalding/safeyolo, and approve it once, for the session, or remembered

None of these widens a capability. Each answer applies inside what you already authorised.

The same pattern, many services

  • GitHub over HTTPS, including Git pushes behind a risk approval
  • Docker and Compose, with each management request checked against the gateway capability
  • Coding-client subscriptions: Claude Code and Codex logins stay in the host vault and are renewed on the host
  • Services hosted by other agents, shared through the same gateway
  • Your own APIs, described in YAML, with optional effect models that assess what a permission could do

What SafeYOLO guarantees

  • The real credential is never in the sandbox
  • A token works only for its agent, capability and destination
  • Unknown secrets in outbound requests need approval before they leave

What it does not do

  • Override the service's own permissions for the account you chose
  • Make a capability safe if it can execute commands: approving it delegates that authority
  • Protect logins a host script copies into a guest, which is a separate, weaker option
