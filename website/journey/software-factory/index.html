Three roles, one room

SafeYOLO's own factory separates coordination, implementation and independent review. The shipped backlog example binds those roles to three Codex agents in one shared Coord room:

RoleAgentDoes
CoordinatorrelayTakes your direction, reads the backlog and creates Work. It is the only role you talk to.
OwnerforgeClaims Work, implements it, runs tests, publishes the exact output and completes execution.
ReviewerlensIndependently reviews that exact output and decides acceptance.

Start the example factory

Use the owning host account with an installed SafeYOLO instance and prepared guest runtime. In a host terminal, start from the SafeYOLO repository root. These commands select the default installation and instance at $HOME/.safeyolo. For another instance, change both paths.

Replace /work/relay, /work/forge and /work/lens with three existing, owned repository workspaces. Keep the installation outside those workspaces. Setup shows the exact role contracts before asking you to approve their immutable snapshot. It prepares the roles and asks for each role's own login or supported provider configuration when needed; it does not copy host or peer credentials.

For a missing checkpoint, confirm fresh identities only if those identities or room memberships have never received targeted attention in any configured room. Valid checkpoints resume without that confirmation.

"$HOME/.safeyolo/bin/safeyolo" --instance-dir "$HOME/.safeyolo" start
"$HOME/.safeyolo/bin/safeyolo" --instance-dir "$HOME/.safeyolo" factory setup docs/factories/backlog-native/backlog.toml --workspace coordinator=/work/relay --workspace owner=/work/forge --workspace reviewer=/work/lens

Editing a contract requires a new snapshot approval and staging before running roles use it.

Setup reports running only after all roles pass the readiness checks. If it stops short, follow its named prerequisite in the setup and recovery guide. The guide also gives the explicit manual commands. Repeat setup after correcting the prerequisite; it reuses saved choices and healthy running roles.

After setup reports running, send direction from the same host account and instance:

"$HOME/.safeyolo/bin/safeyolo" --instance-dir "$HOME/.safeyolo" factory send backlog 'Work the backlog in priority order.'

What native Work enforces

  • Assignment and claims. The example permits relay to create Work and the assigned owner to claim execution.
  • Exact-output review. Publishing an immutable output creates lens's required check for that output. A changed output needs a new check.
  • Execution completion. Forge explicitly completes its attempt before waiting for review. A blocked or failed attempt also completes execution; this does not establish acceptance.
  • Independent acceptance. Lens answers the check and separately decides acceptance. It must be a different participant from forge. Relay integrates the unchanged accepted candidate.

Add checks and service access when needed

The shipped Factory TOML selects roles, checks and acceptance authority. It does not configure executable jobs, service credentials or remote hosts. Each needs separate operator adoption in the selected instance.

With adopted Work bindings, an admission job can check an issue's author before delegation, and an output job can hold acceptance until its predicate passes for the exact retained bytes. An optional after_complete action can post an execution result. That action follows execution completion, including blocked attempts; it is not an acceptance or integration announcement. A failed action cannot undo completion and must not be retried blindly.

With configured service-gateway grants, agents use scoped tokens while the proxy injects host-held GitHub or model credentials. Separately adopted host-executor bindings permit signed operations on remote machines without giving agents the signing key. Factory setup alone supplies neither integration.

What the example gives you

  • Independent acceptance of the exact published output
  • Separate execution and acceptance records
  • Running roles bound to the approved, staged snapshot

What setup does not do

  • Establish software correctness: the reviewer must inspect the result
  • Adopt executable gates, credential custody or remote-host access
  • Turn role instructions into additional permissions
