Most sandboxes are a cage

A sandbox that only says no keeps an agent safe and useless. The agent hits a wall, guesses at the cause, and stops to ask you. SafeYOLO is built the other way round: the sandbox is a place where the agent can do real work, and SafeYOLO talks back.

What the agent gets

  • Its own Linux machine with guest root through sudo, a persistent home and your selected workspace
  • Tools that stay: language runtimes and CLIs installed with mise persist across restarts, and distro packages are available for system dependencies
  • Full terminals, plus ordinary cron and at scheduling inside the guest
  • Browsers inside the guest, with an optional desktop you can watch or take over through a token-gated preview
  • Docker inside the sandbox on Linux, with builds and Compose applications running under the sandbox's own outbound policy
  • Ways to share what it builds: with other agents through the service gateway, or with you on the host's localhost or your tailnet
  • Skills staged at launch that teach it how SafeYOLO works

What the agent can ask

Through the Agent API, answered by the checkpoint through the agent's own socket:

SituationThe agent
A request came back 428 or 403Reads the exact reason with /explain
It is about to need a new hostChecks with /lookup before asking you
It is being rate-limitedReads its budgets and circuit breakers
It needs a serviceRequests one named capability, with a reason
It needs a policy changeProposes the exact snapshot for you to approve
You should see its browserRequests a desktop preview

What you do

Launch an agent on a workspace, choosing its harness. For Claude Code and Codex subscriptions you can keep the login in the host vault:

safeyolo agent launch /path/to/workspace --name alice --harness claude --authentication host-vault

Then let it work. When it needs something outside policy, you get one specific request with its scope, and decide it in the CLI, in Command Centre on macOS, or through a delegated reviewer.

What happens when it hits a wall

  1. The agent calls a host its policy does not cover and gets 428: Network access requires approval.
  2. It reads the reason with /explain, instead of guessing or retrying.
  3. If the work genuinely needs that host, it tells you the exact destination and why, as a pending approval.
  4. You approve or deny it once. The decision and its reason are recorded.

What SafeYOLO guarantees

  • Guest root never becomes host root
  • The only route out is the agent's own socket
  • An agent's requests carry its identity, which it cannot change

What it does not do

  • Protect files in a writable mount from the agent working in them
  • Keep OS package changes under Linux gVisor after a stop; persistent home and caches remain
  • Run nested Docker on macOS: the qualified configuration is Linux with gVisor
