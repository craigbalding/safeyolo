# Mattermost coord operator adapter

The Mattermost adapter is an optional operator-facing projection of selected
coord rooms. Coord remains authoritative. Mattermost is not a coordination
backend, its threads are not trust evidence, and the bot is never registered
as an agent or coord principal.

The first implementation uses Mattermost's supported REST API v4 with a
dedicated non-admin [bot account and bot access
token](https://developers.mattermost.com/integrate/reference/bot-accounts/).
It polls [channel
posts](https://github.com/mattermost/mattermost/blob/master/api/v4/source/posts.yaml)
and creates posts through the same API. It does not require an inbound webhook,
public callback, PikaPods extension, or Mattermost plugin.

## Trust and message shape

Outbound posts display the SafeYolo-generated envelope in one inert JSON code
block and the sender-authored body in a separate inert JSON code block. ASCII
mentions, HTML delimiters, controls, and Unicode ordering controls are escaped;
the body cannot render as the canonical attribution above it. Large bodies are
explicitly truncated with their original byte count and SHA-256 digest.

Inbound text is accepted only when all of these facts agree:

- the bot token identifies the configured active bot;
- the configured operator ID identifies one active non-bot Mattermost user;
- a one-to-one configured channel/coord-room mapping exists;
- the post is an unedited, undeleted reply by that exact operator;
- the Mattermost thread root is a post that this adapter durably correlated to
  a specific coord message in the same room and channel; and
- the Mattermost post ID has not already been consumed.

Accepted text is appended with the same local trusted operator call used by
`safeyolo coord chat`. The resulting coord envelope has canonical
`sender_kind=operator`. Mattermost usernames and body text are never used as
attribution. The active non-bot operator identity is revalidated on every
bounded sync cycle, so deactivation after daemon startup fails closed before
another trusted append. The body is a small structured `text/plain` document containing
the external post/root IDs and target coord message ID; those correlations are
context, not coord authority.

Reply normally to send operator text. The following exact first-word syntax
emits a typed action document without executing an action:

```text
!safeyolo acknowledge optional note
!safeyolo approve optional note
!safeyolo reject optional note
!safeyolo defer optional note
!safeyolo revise optional note
!safeyolo publish optional note
!safeyolo open-issue optional note
```

Unknown or malformed `!safeyolo` commands are ignored. This vocabulary is an
input contract for later workflows; the adapter does not approve, publish, or
open anything itself.

## Operator-owned setup

On a fresh or self-hosted Mattermost deployment, bot creation may initially be
disabled. Before creating the dedicated SafeYolo bot, a Mattermost System Admin
must open **System Console > Integrations > Bot Accounts**, set **Enable Bot
Account Creation** to `true`, and save the setting. This is the standard
Mattermost bot-account setting; the adapter does not require an Enterprise
license, trial feature, plugin, or PikaPods-specific capability.

No existing SafeYolo repository file or `~/.safeyolo/config.yaml` entry should
be changed. Create these two new operator-owned files:

1. `~/.safeyolo/mattermost-bot-token`, mode `0600`, containing only the bot
   access token generated by Mattermost.
2. `~/.safeyolo/coord-mattermost.toml`, containing:

```toml
version = 1
server_url = "https://YOUR-MATTERMOST-ORIGIN"
bot_token_file = "~/.safeyolo/mattermost-bot-token"
bot_user_id = "26_CHARACTER_MATTERMOST_BOT_USER_ID"
operator_user_id = "26_CHARACTER_MATTERMOST_OPERATOR_USER_ID"
state_file = "~/.safeyolo/data/coord-mattermost.sqlite3"
poll_interval_seconds = 2.0

[[rooms]]
coord_room = "ROOM_NAME"
channel_id = "26_CHARACTER_MATTERMOST_CHANNEL_ID"
backfill = false
```

Supply the exact HTTPS origin of the managed Mattermost server and the IDs
returned by that server. Add the dedicated bot **directly as a normal member**
of every channel named by a `[[rooms]]` mapping. Do not use an invitation flow;
an invitation is not channel membership for this adapter. Do not grant the bot
System Admin. Ensure the local coord operator already has `send,receive` on
each mapped room. Every coord room and channel ID may appear only once.
`backfill=false` starts after current coord history and Mattermost channel
history; use `true` only when intentionally projecting all retained coord
history.

The adapter creates the `state_file` itself with mode `0600`. It also creates a
mode-`0600` sibling process-lease file by appending `.lock` to that path (the
example becomes `~/.safeyolo/data/coord-mattermost.sqlite3.lock`). Do not
pre-create, edit, or replace either file. The separate lease file prevents one
adapter process from competing with another without interfering with SQLite's
own database locks, including on macOS.

The database stores only mapping cursors and correlation/idempotency records,
not the bot token. Once a state file is bound to a server, operator, and room
mapping, configuration drift fails closed. Use a new empty state path for an
intentional remapping after the old adapter process is stopped and its pending
records are checked.

Validate the exact setup without relaying messages:

```sh
chmod 600 ~/.safeyolo/mattermost-bot-token
safeyolo coord mattermost check --config ~/.safeyolo/coord-mattermost.toml
```

Run one bounded trial cycle, then start the foreground long-running adapter:

```sh
safeyolo coord mattermost run --config ~/.safeyolo/coord-mattermost.toml --once
safeyolo coord mattermost run --config ~/.safeyolo/coord-mattermost.toml
```

To restart, stop that foreground process with `Ctrl-C` (or have the host
supervisor stop it), then run the same long-running command again. Only one
adapter process may own a state file at a time.

## Delivery and failure semantics

The SQLite state suppresses inbound replay across retries/restarts and marks an
outbound projection pending before calling Mattermost. Each outbound post also
carries a deterministic correlation property. After an interrupted request,
the adapter reconciles a visible matching post; it refuses to retry when the
remote outcome cannot be established. Likewise, an interrupted coord append
is not replayed automatically: the unresolved inbound pending record stops the
adapter until the operator reconciles it. The daemon holds its state-file lease
for its complete lifetime, including quiet sleeps. This deliberately prefers
an operator-visible gap over duplicate trusted operator messages.

An authentication, identity, mapping, malformed-response, ambiguous
correlation, or unresolved-pending error stops the foreground process with a
sanitized message. The bot token is never placed in a URL, command line,
repository file, state database, or error output.

The repository test harness exercises the setup against an API-compatible
fake Mattermost server, including bot/operator/channel checks, real HTTP JSON
shapes, attribution, actions, malformed posts, replay/restart, and uncertain
delivery. A live managed trial still requires the operator-owned server URL,
token, user IDs, channel ID, and channel membership listed above.
