# Author a check or action

Choose the boundary before writing the checker. A required check before an
operation can prevent that operation. Verification after output production can
hold acceptance of those exact bytes. A durable action after completion can
report or follow up; it cannot undo an external effect. Native Work bindings
cover admission, output acceptance and completion. Existing request-stage rules
cover mediated HTTP requests. A GitHub merge or external release needs its
own enforcing boundary.

Read [engine selection](references/engines.md) when choosing a runtime or
explaining platform, process, filesystem, privilege or performance differences.
Read [the installed walkthrough](references/walkthrough.md) for prerequisites,
the GitHub-author example, the small JSON-artifact check and failure inspection.

Identify the selected host, executable/version and instance root. Read the
saved configuration and active policy separately. An ordinary guest can prepare
source and a proposal; the instance owner adopts it through existing host
commands. Keep administrative and provider credentials outside the workload.
Existing standing grants avoid repeated routine approvals.

Develop against the logical request/result contract: policy owns inputs,
artifacts, engine, capabilities and limits; invocation supplies the subject.
Use the bundle's Rust `ServiceCheck` or Python `service_checker.py` as the
working example. The walkthrough includes a runnable offline test for a working
Python copy and preparation with `--bundle` for proposed bytes. Test a real
positive result, predicate mismatch, malformed or missing evidence, denied
capability and bounded failure. A successful process
exit does not establish the predicate. A source fixture establishes its own
scope; it does not prove the selected installed runtime.

In the proposal, explain selected inputs, disclosed data, destinations and
methods, credential custody, execution/evidence bounds, effects, freshness and
failure behavior. Declare passive lookups separately from retaining or active
operations. Select only capabilities the workload needs. Use the existing
policy/service check, preview and adoption mechanisms. The preparing agent
cannot approve its own checker or weaken a required binding.

For automatic issue admission, consume the exact `checked_input` retained with
the Work's automatic evidence. Do not silently replace it with a later fetch,
caller-normalized facts or an issue title. A refreshed admission reads new
evidence. Preserve the captured digest, available revision metadata and
observation time without claiming GitHub remains unchanged afterward.

After an uncertain external effect, inspect the original operation and its
external authority before a retry. Use native Work records and the existing
operator recovery; do not add a queue, scheduler or second result store.
