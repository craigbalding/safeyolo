# Explain outcomes and current assurance

Build the operational receipt from the existing task note, selected
configuration, canonical Work/output/review/signal records and actual consumer
evidence. It is a concise explanation with links to detail, not another store,
mandatory response schema or copy of implementation logs. Keep secrets and
unrelated worker data out of the receipt.
Amend the receipt for the reached result. Reconcile its earlier claims with
new observations rather than appending a conflicting status. Check factual
claims before presenting them; model exit status does not verify the prose.

## Give the operator the useful facts

Include the information relevant to the current task:

| Operator concern | Record and limits to expose |
|---|---|
| What was agreed and what runs? | Accepted intent/design revision; saved, approved and observed active configuration; selected host/instance and durable workers; material differences and pending activation. |
| What can it do? | Effective grants, credentials by reference, data disclosures, selected controls and limits. Distinguish host-derived authority from agent rationale. |
| What happened? | Actual task outcomes and their consumer observations, incomplete/failed operations, unavailable or unbuilt functions and the selected next action. Keep execution completion, independent acceptance and external effect separate. |
| Why is the result relevant? | Task-specific matching reasons and source/edition/artifact provenance. For media, distinguish subtitle metadata from the actual selected edition/track, and link validation/scanning of the exact imported bytes and library readback. Scanner success is not a malware-free guarantee. |
| What protection is evidenced? | Control/version/input bindings, evidence source and observation/expiry, enforcement/test boundary and coverage limits. Distinguish deterministic constraints from taste/usefulness feedback. Missing, stale or unavailable evidence cannot become green. |
| How does operation continue? | Selected on-demand, continuous or scheduled mode, applicable timezone/window, completion policy and unfinished Work. Report observed lifecycle state separately from model activity. |
| How is work restored or upgraded? | Existing retained package/configuration capture status and path coverage, setup-intent notes and recovery pointers. Periodic upgrades use the operator-owned CLI; saved state alone does not prove restoration. |

Link protected or separately owned proof rather than copying or replaying it.
Name its current limit. For example, an accepted catalogue read establishes
neither media import nor the present availability of that title. If active
configuration or a consumer read is unavailable, say which observation is
missing while retaining known saved configuration and valid completed results.
Describe retained provider claims at their observation time. A past
"unavailable" label establishes neither current unavailability nor present
playback eligibility.

Name incremental sharing and output destinations even when existing authority
covers them. Unchanged network/credential authority does not mean that adding
a collaborator shares no new data. Separate task acquisition spend from
model, preparation and operating costs; report only costs actually observed.

Record decisions, manual work and interruptions in the ordinary result. Give
cold/warm elapsed intervals and active operator effort only when observed;
name preparation outside those intervals. Label controlled fixtures, simulated
operator decisions and unavailable measurements. Do not infer cold startup,
autonomy or human effort from a model invocation's duration.

## Recheck relevant changes through existing controls

At activation and after a relevant change, compare the deployed composition
with the reviewed design through its current owners. Use existing policy
status, source/check versions, runtime observations and applicable installed
tests. A compile or saved file does not establish active enforcement.

Identify the affected evidence before reuse. For example, a changed feed
definition, check implementation/configuration/input or job specification can
invalidate the named check's evidence/cache. A changed media artifact needs
controls bound to those bytes. A changed subtitle edition needs evidence for
that edition. A display preference can leave unchanged network authority and
control evidence valid. Do not rerun unrelated accepted proof.

Use each control's adopted freshness/cache and unavailable semantics at the
protected effect. The existing watcher, runtime checks, schedules and audit
own their cadence. See
[named checks](https://github.com/craigbalding/safeyolo/blob/master/docs/policy-checks.md),
[signals](https://github.com/craigbalding/safeyolo/blob/master/docs/signals.md)
and [versioned controls](https://github.com/craigbalding/safeyolo/blob/master/docs/signals.md#adopt-versioned-checks-and-challenges).
No universal daily test, second assurance database or timer service is needed.

When drift or a control failure matters, explain the changed binding, affected
operation, current evidence and operator-selected enforcement response. Use
the existing owner to hold, deny, request a decision or continue as actually
configured; the agent must not substitute its risk appetite. A runtime may be
healthy while the task's required control is unavailable. Fixing configuration
does not establish a passing recheck or restore an expired grant.

For a controlled demonstration, retain the baseline, introduce only the
authorized relevant change, observe detection and enforcement, then restore
through the current owner and observe the affected recheck. Inspect uncertain
effects before repeating them. Keep control failure, detection and restoration
observations separate.

Use existing signal/update identity and resolution for material changes. Deliver
results, exceptions and useful improvement suggestions through the selected
channel/cadence. An unchanged condition or quiet period needs no repeated
suggestion, approval request or new signal. Do not suppress a new failure by
calling it unchanged, or turn absent observations into a success report.
An unchanged return can need no new operation while existing Work and its
unfinished obligations remain. Say whether new work was created separately
from whether existing work is present or complete.
